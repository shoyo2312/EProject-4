# Demo Seed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `scripts/seed/` toolset that fills a fresh local stack with 50 users, 200 real videos and four months of engagement, admin activity, chat and stories, through the real APIs, then backdates every store.

**Architecture:** `content.py` (static Vietnamese banks + personas) → `scenario.py` (pure, deterministic planner: produces one chronologically sorted event list with planned instants) → `seed.py` (executes the plan over HTTP against service ports, records ids in `ledger.json`) → `backdate.py` (rewrites timestamps/counters in every store from the ledger via `docker exec` CLIs and ES HTTP). Everything resumable from the ledger.

**Tech Stack:** Python 3.12 stdlib only (`urllib`, `json`, `random`, `subprocess`, `concurrent.futures`). Store CLIs inside containers: `psql`, `mongosh`, `cqlsh`, `clickhouse-client`, `redis-cli`. Elasticsearch over HTTP `:9200`.

**Spec:** `docs/superpowers/specs/2026-10-27-demo-seed-design.md`

## Global Constraints

- No third-party Python packages. No new Maven modules. Nothing under `services/` changes.
- Service base URLs (direct, not gateway): auth `http://localhost:8081`, user `:8082`, video `:8083`, interaction `:8085`, story `:8086`, chat `:8088`, notification `:8089`, admin `:8096`. MinIO `http://localhost:9000`, ES `http://localhost:9200`.
- Every API response is `{success, data, code, message, timestamp}`; the seed unwraps `data`.
- Turnstile dummy token: `XXXX.DUMMY.TOKEN.XXXX`. Demo password: `Demo@12345`. Emails `<username>@example.com`.
- Timeline: `T0 = 2026-06-27T00:00:00+07:00`, `T1 = now`. Random seed default `2026`.
- Ledger path: `<media-dir>/ledger.json`. Media dir default `~/Projects/EProject/EProject4/seed-media`.
- Container names: `tt-postgres-auth` (db `auth_db`), `tt-postgres-user` (`user_db`), `tt-postgres-admin` (`admin_db`), all `postgres/postgres`; `tt-mongodb` (`root/password`, authSource `admin`); `tt-cassandra` keyspace `interaction_ks`; `tt-clickhouse` db `analytics_db` user `default` pw `clickhouse`; `tt-redis`.
- Create pass is strictly in planned order within a video and within a user (Snowflake ids order the lists).
- Text banks must not contain any term from `libs/moderation-lib/src/main/resources/moderation/blocklist-vi.txt` (severity 3 → 422 + strike).
- Never re-key Cassandra comments; re-insert only `likes_by_user`, `reposts_by_user`, `saves_by_user_time`.
- Backdate only videos that are `PUBLISHED`, `PENDING_REVIEW`, `TAKEN_DOWN` or `REJECTED` (never `PROCESSING`/`PENDING_MODERATION`).

## Review Focus

1. A comment refused with 422 or `COMMENTING_RESTRICTED` must not abort the run; the persona's later comments are skipped and the plan continues (test in Task 5).
2. A video the pipeline holds (`PENDING_REVIEW`) beyond the 6 the scenario wants must be restored by the admin phase before engagement, otherwise its planned likes 404 (Task 6 `early_restore`; engagement filters on the ledger's final status, not the plan).
3. Re-running `seed.py` after a crash must skip objects already in the ledger (test in Task 3: second run of the users phase performs zero registrations).
4. Backdating a like must write the same millisecond to `likes_by_video` and the re-inserted `likes_by_user` row (test in Task 7: cqlsh readback of both rows equal).
5. Pending reports must survive `StaleReportSweep`: every PENDING report is either < 30 days old or uses a non-expiring reason (test in Task 2 `--check`).

### Task 2: Scenario planner

**Files:**
- Create: `scripts/seed/scenario.py`
- Test: `scenario.py --check` (self-check, no separate test file)

**Interfaces:**
- Consumes: Task 1 names; `manifest.json` (`videos[]: {id, topic, file, width, height, duration, tags}`, `avatars[]`, `stories[]`).
- Produces: `build(manifest: dict, seed: int = 2026, now: datetime | None = None) -> dict` returning
  - `users: list[dict]` — persona + `join_at: str` (ISO UTC ms) + `avatar: str` (relative file) + `settings: dict | None` (`{"privateAccount": true}` / `{"commentKeywords": ["quảng cáo","inbox"], "filterSpamOffensive": true}`), sorted by `join_at`.
  - `follows: list[dict]` — `{follower, following, at}` (usernames).
  - `videos: list[dict]` — `{key: "<topic>/<id>", owner, title, description, tags, visibility, at, held: bool, views, completions, likes, taken_down_at: str|None}` sorted by `at`; `held` true for exactly 3 (HELD_CAPTIONS).
  - `events: list[dict]` — every engagement in one list sorted by `at`, each `{kind, at, actor, ...}` with kinds: `like {video}`, `comment {video, text, cid}`, `reply {video, parent_cid, text, cid}`, `comment_like {video, cid}`, `share {video}`, `repost {video}`, `save {video}`. `cid` is the planner's own comment key (`"c123"`), used by later events and by admin actions.
  - `chats: list[dict]` — `{a, b, messages: [{from, text, at}]}`.
  - `stories: list[dict]` — `{owner, file, caption, visibility, at}` (all within the last 20 h).
  - `admin: list[dict]` sorted by `at` — `{kind, at, ...}` with kinds: `report {reporter, target_type, target, reason, outcome: pending|DISMISS_REPORT|<ACTION_TYPE>, ban_days}`, `ban {user, days: int|None, reason}`, `warn {user, reason}`, `takedown {video, reason}`, `remove_comment {video, cid, reason}`, `restore {video: None}` (bound to a real held video at run time). Targets reference usernames / video keys / `cid`s.
- Rules the builder encodes (from spec §4): join curve front-loaded with 2 joins in the last 14 days; 8–16 videos/week, ≤ 4/day, hours weighted 11–14 and 19–23 +07; Zipf counters (rank 1–10 → 20 000–60 000 views, 1 000–4 000 likes; median 300–2 000 / 20–150; tail < 100); likes/comments/shares/reposts/saves planned per video with ratio comment ≈ 4 %, share ≈ 2 %, repost ≈ 1 %, save ≈ 3 % of likes, each with 60 % in the first 3 days after `at`; **the number of likes sent through the API is capped at `min(likes, 40)` per video and the remainder is added to the counter in backdate**; follows ~600, creators followed by 60–90 % of users; a `follow` to a private account is emitted as `kind=follow_request`; engagement actors exclude `spam`/`temp_ban` personas after their ban instant and never engage FRIENDS videos unless mutual followers, never PRIVATE or held videos; comments unique per video; admin list exactly: 30 reports (12 VIDEO, 8 USER, 10 COMMENT; outcomes 3 TAKEDOWN_VIDEO, 2 BAN_USER, 4 REMOVE_COMMENT, 5 WARN_USER, 8 DISMISS_REPORT, 8 pending), permanent ban of `spam` 30 days ago (`days=None`), ban of `temp_ban` 2 days ago with `days=5`, 10 `remove_comment` (6 on the two banned personas' comments, ≤ 1 per other author, none on `PERSONAS[0]`), 2 `restore`; pending reports either `at > now - 29d` or reason in `NON_EXPIRING_REASONS`.

### Task 7: backdate.py

**Files:**
- Create: `scripts/seed/backdate.py`

**Interfaces:**
- Consumes: ledger sections from Tasks 3–6 and the plan (rebuilt from the same seed) for planned instants and counters.
- Produces: `main(media_dir, seed)` running, in order, `backdate_auth`, `backdate_user`, `backdate_video`, `backdate_es`, `backdate_reco`, `backdate_cassandra`, `backdate_chat`, `backdate_notifications`, `backdate_admin`, `backdate_clickhouse`, `flush_redis_caches`. Each builds one script string and pipes it to the container CLI once per store (not one `docker exec` per row). Idempotent.
- Exact writes:
  - auth: `UPDATE users SET created_at=:t, updated_at=:t, email_verified_at=:t, last_login_at=:t WHERE id=:id`; `UPDATE auth_security_events SET created_at=:t WHERE user_id=:id`.
  - user: `user_profiles` by `user_id`; `user_follows` by `(follower_id, following_id)` → follow `at`; `user_follow_requests` by `(requester_id, target_id)`.
  - video (`mongosh video_db`): per id `$set {createdAt: at, publishedAt: at+90s, updatedAt: at+90s, "moderation.checkedAt": at+60s, "textModeration.checkedAt": at, viewCount: views, likeCount: likes}`.
  - ES: `_bulk` `{"update":{"_id":id}} {"doc":{"createdAt":"<yyyy-MM-ddTHH:mm:ss.SSS UTC>","viewCount":views,"likeCount":likes,"commentCount":<ledger count>,"shareCount":<ledger count>}}`.
  - reco (`redis-cli`): `ZADD reco:video:published <epoch_s> <id>`; `ZADD reco:tag:<tag> <epoch_s> <id>` per tag; `ZADD reco:video:watches <views> <id>`; `ZADD reco:video:completions <completions> <id>`.
  - Cassandra (`cqlsh -k interaction_ks`): comments `UPDATE comments_by_video SET created_at=:ms WHERE video_id=:v AND comment_id=:c`; shares `UPDATE shares_by_video SET created_at=:ms WHERE video_id=:v AND share_id=:s`; comment likes `UPDATE comment_likes SET created_at=:ms WHERE comment_id=:c AND user_id=:u`; likes: read current `created_at` from `likes_by_video` (one `SELECT … WHERE video_id=:v` per video, parsed), then `DELETE FROM likes_by_user WHERE user_id=:u AND created_at=:old AND video_id=:v; INSERT INTO likes_by_user (user_id, created_at, video_id) VALUES (:u, :ms, :v); UPDATE likes_by_video SET created_at=:ms WHERE video_id=:v AND user_id=:u`; same shape for reposts (`reposts_by_video`/`reposts_by_user`) and saves (`saves_by_user`/`saves_by_user_time`); counters `UPDATE video_counters SET view_count = view_count + :views, like_count = like_count + :extra WHERE video_id=:v`, `extra = planned likes − API likes`, applied once (ledger flag `counters_applied`).
